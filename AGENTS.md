## Data and API rules

- Use the database field names and types directly in requests, responses, and frontend types. Update all callers, OpenAPI, and tests together when changing a contract.
- Monetary fields are `amount`: integer currency minor units, never floating-point money. SGD 6.50 = 650; JPY 650 = 650; KWD 1.234 = 1234. The current maximum is enforced in the schema/core. Use `payment_method` for payment labels.
- `kind` distinguishes `expense` and `income`; both store positive `amount`. Income never consumes spending budgets. Circle income reverses the expense balance deltas: `paid_by` identifies the recipient who owes the allocated shares.
- Recurrence supports expenses and income in both ledgers. `recurrence_interval` selects every 1–365 days/weeks/months/years (0 is stored when disabled); `recurrence_weekdays` contains ISO weekdays (Monday=1, Sunday=7); empty uses the original weekday. Weeks start Monday and every-N-week schedules stay anchored to the entry week. `recurrence_month` chooses a yearly month (1–12; 0 uses the entry month). `recurrence_day` applies to monthly/yearly schedules: 0 keeps the original date, -1 means last day, and 1–31 chooses a date clamped in shorter months. Explicit weekdays and monthly/yearly dates can recur later in the entry week/month/year; intervals remain anchored to that period. Use the saved schedule timezone, including downtime catch-up. Preserve transactional generation/cursor advancement, original month-end anchors, author/membership checks and visible pause errors. Editing a schedule affects future entries; stopping/deleting it preserves generated history.
- Circle shares use `member` (membership ID). Even inputs contain only `member`; exact inputs add integer `amount`; percentage inputs add integer `percentage_bp` (6000 = 60%). Saved shares contain the calculated `amount`. Preserve deterministic largest-remainder rounding.
- Circle `owner` is a user ID. `paid_by`, share members, settlement participants, and `created_by` are membership IDs. Never interchange the two kinds of IDs.
- Relations retain their stored IDs. Public related data goes under `expand.user` or `expand.circle`; do not replace relation IDs with objects. Keep profile projections limited to public fields.
- Key creation accepts a future timezone-explicit `expires_at`, or an empty string for no expiration. Duration choices are presentation logic in the form. Unsupported request fields are rejected.
- `exchange_rates.quotes` and `dates` have the same structure in storage and responses. Preferences and default categories are persisted during initialization; do not synthesize legacy settings on reads.
- Validate input on the server even when a frontend form already validates it. Preserve ownership checks, API-key scope separation, hidden secrets, and server-managed provenance. Never expose superuser credentials to the browser or automation clients.
- API secrets are shown once and stored as hashes. Key metadata projections must not expose secrets/hashes. Usage writes must not overwrite concurrent revocation.
- API-key Circle expense creation uses `expenses:write` and checks the key and active membership inside the write transaction. The payer, creator and initial 100% share are always the key owner's membership; clients cannot set payer, split, source or recurrence fields. Only the website's session routes can edit allocations. Currency defaults to the Circle currency and categories come from that Circle.
- Idempotency is scoped to the user across API keys and both creation endpoints, and lasts 24 hours from the original ledger's server `created`, not `occurred_at`. Locked `api_transaction_retries` records retain the accepted request, original destination and transaction ID independently of mutable/deleted ledger records. Retry snapshots live only in this collection; expenses have no idempotency fields. Move receipts remain protected. Identical retries replay the current expense; changed data or a changed explicit Circle conflicts even after edits, category renames/archiving or preference changes. A deleted transaction returns 410; Circle replays still require active membership and an existing Circle. Reuse after expiry creates a new expense. Atomically release expired retry receipts without deleting expenses or extending the window through retries/edits. Upgrades copy existing personal snapshots and creation times without resaving ledger history.
- `preferences.default_api_circle` is empty for personal API creation or an active Circle ID selected in Settings. It applies to new expenses at `POST /api/expenses/transactions` across all user API keys; the request keeps `merchant`, mapped internally to Circle `title`. The stored response uses its actual field names and adds `destination`, `replay` and `idempotency_expires_at`. Omitted currency/category use the destination defaults; supplied categories are validated there. Circle imports create no personal copies and retain 100% self allocation. Explicit Circle URLs and existing retries keep their destinations. Retain unavailable default Circle IDs and return 404 on imports rather than falling back silently; unrelated preference edits and clearing/changing the default remain possible. Website requests use category IDs. API personal reads return category IDs with `expand.category`; name-based automation creation payloads are unchanged.
- Circle writes must check authorization and balances inside their transaction. Keep version checks for stale edits, verified-email invitation matching, and author/owner restrictions. Preserve former member IDs/history; historical changes must not alter their balances. Settlements cannot overpay or mix currencies and never move money.
- Recorded repayments can be edited by their original author or the Circle owner using their current version. Validate financial changes against current balances with the original repayment reversed, preserve the repayment ID/creator/created timestamp, and recalculate suggestions from the saved ledger. Notes/date-only edits must remain possible after later ledger changes without changing any balances.
- Deleting accounts marks retained memberships inactive; deleting an owner account cleans up owned circles. Do not derive substitute membership status on reads.
- Moved personal expenses retain `moved_to` and `moved_circle` as server-managed receipts to preserve API retries. Exclude them from every personal list, report, export, and currency query. Never clear these markers on Circle deletion or allow native clients to revive or edit receipts. Circle entries preserve their original ID, money, timestamps and provenance; they initially assign 100% to the moving membership.
- Circle expenses and income can move to the paid-by user’s personal ledger through the session-only move-to-personal route. Check active membership, payer user and version inside the transaction; author/owner status alone grants no move permission. Move the full amount, map to an active personal category, preserve currency, timestamps, provenance and recurrence checkpoints, remove the Circle split, and protect former-member balances. Recorded repayments remain. Locked `circle_personal_moves` receipts retain source snapshots (including receipts/shares) and make retries idempotent; create a fresh personal ID so earlier personal-to-Circle receipts remain immutable. Circle API retries retain their original destination and return 410 once that entry leaves the Circle; never recreate it automatically.
- Personal expenses, budgets and Circle entries store category relation IDs. An empty budget category means the overall monthly budget. Website/session requests use IDs; API-key expense creation accepts category names and resolves them server-side at that boundary. Related labels are exposed through `expand.category`; report buckets add `category_name`, and combined feeds add `budget_category_name`. Category renames update the category row only, preserving ledger IDs, timestamps, schedule cursors and Circle edit versions. Archiving/disabling preserves history. Ordering includes archived categories and checks `previous_ids` before saving; do not overwrite concurrent reorder changes.
- New personal expense/income forms use `preferences.default_entry_currency` (empty follows the main currency) and separate `default_expense_category` / `default_income_category` category relations (empty uses Other, then the first active category). Category defaults must belong to the user and be active; renames retain IDs, and archiving clears matching defaults atomically. Disabling the preferred currency resets it to follow the main currency. These defaults do not change edits, budgets, recurring generation, Circle entries or API imports.
- Dates are stored as instants; the account timezone controls entry, report boundaries, daily grouping, and exports. Preserve the original instant when a minute-only picker is unchanged, including seconds and daylight-saving overlaps. Monthly report boundaries use the first valid local instant when midnight is skipped or repeated; entry pickers still reject nonexistent local times. Test daylight-saving boundaries. Defaults are SGD and Asia/Singapore.
- Persist `preferences.time_format` as `24h` (default) or `12h`. Apply it to all displayed times, date/time picker controls, recurring schedule timestamps and local export columns. Keep picker form values in 24-hour wall-clock notation, API/UTC timestamps in ISO format, and Excel dates typed; changing display format must not change instants or recurrence schedules.
- `preferences.show_circle_transactions` defaults to false and controls dashboard recent transactions, the Transactions page and its exports. Enabled lists include personal entries and positive own Circle expense/income allocations, including retained historical allocations for inactive memberships. Exclude settlements, zero/unallocated entries and moved receipts. Keep stored Circle `amount`/`category` intact; return `allocated_amount`, `budget_category` (personal ID) and `budget_category_name` separately. Circle actions must open Circle details rather than personal edit/delete routes. Budget totals do not depend on this display setting.
- Reports aggregate all matching records on the backend. Do not calculate monthly totals from paginated browser results.
- `preferences.include_circle_in_budgets` defaults to true for new and upgraded accounts and controls whether personal spending summaries and monthly budgets include positive allocated shares of Circle expenses, using the expense instant and the account's report boundaries. Count shares rather than payer totals, retain historical shares for inactive memberships, and exclude Circle income and repayments. Match Circle category names to personal categories by exact name, then unique case/whitespace-insensitive name; fall back to the personal Other category or the report's Other bucket. Do not create personal expense copies or change Circle categories/balances. Moved personal receipts remain excluded to prevent double counting.
- Exchange rates are reference estimates using the latest cached observations, including for historical expenses. Preserve original amounts, per-expense rounding, the shared refresh lease, failure throttling, stale/missing-rate warnings, and age limits. Never recompute Circle debts from exchange rates.

## Migrations and deployment

- The Next.js app runs on Vercel; PocketBase runs separately. Keep backend work in PocketBase hooks/migrations unless a requirement actually needs another service. Preserve the existing `users` collection and OAuth/OIDC settings.
- The frontend URL is `expenditure.tkkr.dev`; the configured PocketBase URL is `e.tkkr.dev`. `NEXT_PUBLIC_POCKETBASE_URL` is public and baked into the client at build time. Do not change a running server or deployment without authorization.
- Prepare installable PocketBase files for the user; do not assume server access. Copy all hook files, including JSON/CJS modules, together with all unapplied migrations. Keep the matching frontend/schema/hooks coordinated.
- Add new migrations; do not rewrite applied history or remove old migrations because they contain earlier field names. Historical migrations are not runtime compatibility aliases. Back up before applying; some down migrations delete collections/data.
- Current backend status is version 25 in `main.pb.js`, checked by workspace startup. When a contract changes, update both the reported and required version together.
- The category-relation migration requires backup restoration to roll back; it removes duplicate retry fields after the existing retry migration has populated immutable receipts. User deletion removes personal expenses/budgets/preferences before categories inside one transaction.
- Test fresh installation and upgrades with existing records. Preserve IDs, amounts, timestamps, provider configuration, and ledger balances unless the requested change explicitly requires otherwise.
- PocketBase 0.40.6 is the validated server version; do not confuse it with the JS SDK version. Read `package.json` for installed frontend/tool versions.
- OAuth callback uses the PocketBase URL with `/api/oauth2-redirect`. Preserve exact allowed origins and realtime/SSE support. The frontend does not need a separate OAuth callback or privileged API proxy.
